# Совместный бой напрямую — WebRTC / одна Wi-Fi-сеть

GitHub Pages раздаёт приложение; браузер создателя партии хранит и проверяет главное состояние. Отдельного игрового или signaling-сервера нет. `RTCPeerConnection` создаётся с `iceServers: []`: STUN/TURN не используются. Проверки реальных устройств в конкретной сети ещё нужны; одна Wi-Fi-сеть должна разрешать прямую связь клиентов друг с другом.

## Подключение двух игроков

1. Оба открывают сайт и сохраняют свои ростеры.
2. Первый: **Бой → Создать совместный бой**, имя и ростер → **Создать приглашение**.
3. Хозяин копирует полный текст приглашения и передаёт второму игроку удобным способом.
4. Второй: **Бой → Подключиться к игроку**, имя/ростер, вставить приглашение → **Подготовить ответ**. Передаёт полный текст ответа хозяину.
5. Хозяин вставляет ответ → **Соединить устройства**. После установления связи окна закрываются; появляется «● Прямая связь».
6. Каждый выбирает свой отряд и до пяти тактик. Общие миссии, лимит Threat и приоритет видят оба. Когда оба нажали «Я готов», начинается общий бой.

Тексты подключения длинные: они содержат сетевые параметры и криптографические отпечатки WebRTC. Короткий код сам по себе без сервиса поиска не заменяет этот обмен. Камера и микрофон приложению не требуются; QR-сканирование в этой версии не реализовано.

Страницу хозяина нужно сохранять открытой. После перезагрузки/разрыва: открыть сохранённую совместную партию у хозяина и обменяться новым приглашением и ответом. У второго игрока — «Переподключиться». Автоматического обнаружения по сети или восстановления после полного закрытия браузера без обмена новыми текстами нет. На iPad поведение при блокировке экрана и долгом уходе в фон ещё следует проверить на физическом устройстве.

## Согласованность

- Любое действие гостя получает operationId и исходную revision. Хозяин последовательно проверяет и применяет команды, сначала сохраняет результат локально, затем подтверждает и рассылает состояние.
- При конфликте ревизии гостевая очередь применяет исходное действие к свежему состоянию и повторяет с тем же operationId. Список принятых ID хранится вместе с комнатой: потеря ответа и перезапуск хозяина не должны дублировать принятое действие.
- В подготовке каждый меняет только свой отряд. Смена общих условий сбрасывает готовность обоих; начало — после двух подтверждений. Правила комнат общие с Node-сервером: `room-core.js`.
- После старта оба могут менять обе стороны, VP, HP, энергию, состояния, карту и тактики. Раунд, Power Phase и undo — отдельные команды, проверяемые хозяином.
- Изменения рассылаются сразу. Каждые 10 секунд приходит полный контрольный снимок без тяжёлой undo-истории; при неизменной revision DOM не перестраивается. Обычные обновления передают только отсутствующие справочные карты.
- При отсутствии связи новые изменения гостя отклоняются с пояснением. Уже отправленные без подтверждения остаются в очереди текущей страницы до переподключения; перезагрузку с такой очередью браузер предупреждает. Очередь не записывается на диск.
- Передача режется на небольшие части, с ограничением размера и контролем bufferedAmount. Нет скрытых HTTP-запросов игрового API, Google-входа или фонового канала к ноутбуку.

## Сохранения

`mcp-companion-peer-rooms-v1` содержит роль, снимок, а у хозяина — авторитетную комнату с undo и принятыми operationId. `mcp-companion-peer-profile-v1` — локальный ID и выбранное имя. Это браузерное хранилище конкретного устройства, не облачный аккаунт.

Снимок партии также сохраняется среди обычных локальных матчей и попадает в существующий JSON-экспорт. После импорта на другое устройство он является локальной копией: роль хозяина, соединение и идентификатор второго игрока этим экспортом автоматически не восстанавливаются. Исходные данные старого Node-сервера не изменены.

## Проверки и ограничения доказательства

Автоматическая проверка использует два независимых браузерных контекста и настоящий RTCDataChannel. Полностью запрещены внешние HTTP-запросы; ICE-серверов нет. Проверяются обмен текстами, два собственных отряда, готовность, конкурентные HP/VP, undo, перезагрузка хозяина, дедупликация потерянного подтверждения, контрольный снимок, новый раунд и завершение.

На рабочем ноутбуке UDP на собственные VPN- и Wi-Fi-адреса не возвращается даже в отдельной socket-проверке. Поэтому тестам на одном ноутбуке разрешён Chromium loopback-interface (`--allow-loopback-in-peer-connection`); обфускация адресов отключена только в тестовом процессе, а тестовым контекстам даны разрешения media для перечисления интерфейсов. Записи камеры/микрофона нет. Настройки пользовательского браузера, VPN и системы не меняются. Это проверка реального локального RTC-транспорта и логики приложения, **не доказательство успешной связи двух физических iPad через роутер**.

```sh
cd /Users/aslanator/new_projects/painting/mcp-companion
npm ci
npm run build
npm test
npx playwright test tests/e2e/peer-battle.spec.cjs --workers=1 --reporter=list --output=test-results/peer-lan
```

`MCP_PEER_REAL_NETWORK=1` убирает тестовые флаги и разрешения для пробы сетевых интерфейсов хоста. На этом ноутбуке такой сценарий показал failed ICE; не выдавать loopback-результат за исправление сетевых ограничений.

Для реальной проверки: iPad Safari + второй iPad/Android/ноутбук в одной негостевой сети, проверка подключения, частых изменений, сна/возврата, перезагрузки хозяина и восстановления из истории. VPN, client isolation, ограничения mDNS/UDP и браузерные разрешения могут препятствовать прямому соединению; код приложения не отключает эти ограничения и не включает серверный relay как скрытый fallback.

Источники: [WebRTC: peer connections и signaling](https://webrtc.org/getting-started/peer-connections), [MDN: RTCDataChannel](https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel), [Chromium: loopback test switch](https://chromium.googlesource.com/chromium/src/+/refs/tags/133.0.6893.1/content/public/common/content_switches.cc).
